Error handling in Foobara is designed to be **explicit, typed, and discoverable**. Rather than raising ad hoc exceptions, commands declare every error they might produce as structured metadata. This means connectors, generated SDKs, and manifest-driven tooling can enumerate all possible failure modes before a command is ever called — the same way they can enumerate inputs and results.

## Input Errors vs Runtime Errors

Foobara draws a hard line between two categories of errors.

<CardGroup cols={2}>
  <Card title="Input (data) errors" icon="circle-xmark">
    Failures caused by bad input values — wrong type, missing required field, value out of range. The framework generates these automatically during input processing. Their error keys follow the pattern `"data.<attribute>.<symbol>"`.
  </Card>
  <Card title="Runtime errors" icon="triangle-exclamation">
    Failures that occur during command execution, unrelated to a specific input — a divide-by-zero, a record not found, an external service failure. Their keys follow the pattern `"runtime.<symbol>"`.
  </Card>
</CardGroup>

## Declaring Input Errors with `possible_input_error`

Use `possible_input_error` to declare a custom error that is associated with a specific input attribute. The simplest form passes the attribute name, a symbol, and a `message:` option:

```ruby
class Divide < Foobara::Command
  inputs do
    dividend :integer, :required
    divisor  :integer, :required
  end

  result :integer

  possible_input_error :divisor, :divide_by_zero, message: "Cannot divide by zero"

  def execute
    validate_divisor
    perform_division
    quotient
  end

  attr_accessor :quotient

  def validate_divisor
    if divisor == 0
      add_input_error(:divisor, :divide_by_zero)
    end
  end

  def perform_division
    self.quotient = dividend / divisor
  end
end
```

```ruby
outcome = Divide.run(dividend: 49, divisor: 0)
outcome.success?          # => false
outcome.errors_sentence   # => "Cannot divide by zero"
outcome.errors_hash
# => {
#   "data.divisor.divide_by_zero" => {
#     key:          "data.divisor.divide_by_zero",
#     path:         [:divisor],
#     runtime_path: [],
#     category:     :data,
#     symbol:       :divide_by_zero,
#     message:      "Cannot divide by zero",
#     context:      {},
#     is_fatal:     false
#   }
# }
```

## The `Foobara::DataError` Subclass Pattern

For richer errors — including those with typed context data — define an explicit error class inside the command:

```ruby
class Divide < Foobara::Command
  class DivideByZeroError < Foobara::DataError
    def message
      "Cannot divide by zero"
    end
  end

  possible_input_error :divisor, DivideByZeroError

  # ... rest of command
end
```

Both forms are equivalent. The explicit class form is preferred when you need to attach contextual data (see [Error context](#error-context) below) or share the error class across multiple commands.

## Declaring Runtime Errors with `possible_error`

When a failure is not tied to a specific input, use `possible_error` and signal it with `add_runtime_error`:

```ruby
class Divide < Foobara::Command
  possible_error :divide_by_zero, message: "Cannot divide by zero"

  def execute
    validate_divisor
    perform_division
    quotient
  end

  attr_accessor :quotient

  def validate_divisor
    if divisor == 0
      add_runtime_error DivideByZeroError
    end
  end

  def perform_division
    self.quotient = dividend / divisor
  end
end
```

```ruby
outcome = Divide.run(dividend: 49, divisor: 0)
outcome.errors_hash
# => {
#   "runtime.divide_by_zero" => {
#     key:          "runtime.divide_by_zero",
#     path:         [],
#     runtime_path: [],
#     category:     :runtime,
#     symbol:       :divide_by_zero,
#     message:      "Cannot divide by zero",
#     context:      {},
#     is_fatal:     false
#   }
# }
```

<Note>
`add_runtime_error` halts the command immediately by default (`halt: true`). Pass `halt: false` to accumulate multiple runtime errors before returning an unsuccessful outcome.
</Note>

## Error Context

Error classes can carry structured context data — a typed hash of additional information about the failure. This data appears in `errors_hash` under `:context` and is included in manifests so clients know exactly what information to expect.

```ruby
module FoobaraDemo
  module CapyCafe
    class ImportAnimal < Foobara::Command
      class NotACapybara < Foobara::DataError
        context species: :symbol, animal: AnimalHouse::Animal

        def message
          "Can only import a capybara not a #{species}"
        end
      end

      possible_input_error :animal, NotACapybara
    end
  end
end
```

The `context` declaration adds `species` and `animal` to the error's metadata. Consumers of the manifest — generated SDKs, documentation tools — know what fields to expect in the error payload.

## The `errors_hash` Structure

Every entry in `errors_hash` is a hash with the following keys:

<ParamField body="key" type="String">
  Dot-separated fully-qualified error key, e.g. `"data.divisor.divide_by_zero"` or `"runtime.divide_by_zero"`.
</ParamField>

<ParamField body="path" type="Array">
  Attribute path from the command's inputs root to the field that failed. Empty for runtime errors.
</ParamField>

<ParamField body="runtime_path" type="Array">
  When the error originated inside a subcommand, this records the chain of subcommand symbols. Empty for direct errors.
</ParamField>

<ParamField body="category" type="Symbol">
  Either `:data` (input error) or `:runtime`.
</ParamField>

<ParamField body="symbol" type="Symbol">
  The short error symbol, e.g. `:divide_by_zero`, `:cannot_cast`, `:missing_required_attribute`.
</ParamField>

<ParamField body="message" type="String">
  A human-readable description of what went wrong.
</ParamField>

<ParamField body="context" type="Hash">
  Structured context data declared on the error class. Empty hash if none declared.
</ParamField>

<ParamField body="is_fatal" type="Boolean">
  Whether this error represents a fatal (non-recoverable) failure. `false` for most errors.
</ParamField>

## Errors in Manifests (Discoverability)

Every error declared with `possible_input_error` or `possible_error` appears in the command's manifest under `possible_errors`. This is a core part of Foobara's discoverability story: tooling can enumerate all possible failures without running the command.

```ruby
# List all possible error keys for a command
Divide.possible_errors.map(&:key).map(&:to_s)
# => [
#   "data.dividend.cannot_cast",
#   "data.dividend.missing_required_attribute",
#   "data.divisor.cannot_cast",
#   "data.divisor.divide_by_zero",      # <-- our custom error
#   "data.divisor.missing_required_attribute",
#   "data.unexpected_attributes",
#   ...
# ]
```

Via a command connector:

```ruby
require "foobara/command_connectors"

connector = Foobara::CommandConnector.new
connector.connect(Divide)

# Look up the error in the full manifest
connector.foobara_manifest[:command][:Divide][:possible_errors]["data.divisor.divide_by_zero"][:error]
# => "Divide::DivideByZeroError"

connector.foobara_manifest[:error][:"Divide::DivideByZeroError"][:parent]
# => [:command, "Divide"]
```

<Tip>
Because possible errors are part of the manifest, code generators can produce typed error-handling code in client SDKs (Ruby, TypeScript) that matches exactly what your commands can produce — without any manual documentation effort.
</Tip>

## Complete Example: The Divide Command

The following is the full `Divide` command from the README, demonstrating both input error and runtime error patterns in context. Note how `#execute` reads as a self-documenting algorithm.

```ruby
class Divide < Foobara::Command
  inputs do
    dividend :integer, :required
    divisor  :integer, :required
  end

  result :integer

  depends_on Subtract

  # Declare our custom input error
  possible_input_error :divisor, :divide_by_zero, message: "Cannot divide by zero"

  def execute
    validate_divisor
    initialize_quotient_to_zero
    make_operands_positive_and_determine_if_result_is_negative

    until dividend_less_than_divisor?
      increment_quotient
      subtract_divisor_from_dividend
    end

    negate_quotient if negative_result?

    quotient
  end

  attr_accessor :negative_result, :quotient

  def validate_divisor
    if divisor == 0
      add_input_error(:divisor, :divide_by_zero)
    end
  end

  def initialize_quotient_to_zero
    self.quotient = 0
  end

  def make_operands_positive_and_determine_if_result_is_negative
    self.negative_result = false

    if dividend < 0
      self.dividend = -dividend
      self.negative_result = !negative_result
    end

    if divisor < 0
      self.divisor = -divisor
      self.negative_result = !negative_result
    end
  end

  def dividend_less_than_divisor?
    dividend < divisor
  end

  def negative_result?
    negative_result
  end

  def increment_quotient
    self.quotient += 1
  end

  def subtract_divisor_from_dividend
    self.dividend = run_subcommand!(Subtract, operand1: dividend, operand2: divisor)
  end

  def negate_quotient
    self.quotient = -quotient
  end

  attr_writer :dividend, :divisor

  def dividend
    @dividend || super
  end

  def divisor
    @divisor || super
  end
end

# Valid call
Divide.run!(dividend: 49, divisor: 7)   # => 7

# Error case
outcome = Divide.run(dividend: 49, divisor: 0)
outcome.success?          # => false
outcome.errors_sentence   # => "Cannot divide by zero"
```

<Accordion title="Converting an input error to a runtime error">
  The same divide-by-zero scenario can be expressed as a runtime error instead by using `possible_error` and `add_runtime_error`. The behaviour is identical except the error key becomes `"runtime.divide_by_zero"` and the `path` in `errors_hash` is an empty array instead of `[:divisor]`.

  ```ruby
  class Divide < Foobara::Command
    possible_error :divide_by_zero, message: "Cannot divide by zero"

    def validate_divisor
      if divisor == 0
        add_runtime_error DivideByZeroError
      end
    end
  end
  ```

  Use an input error when the problem is clearly attributable to a specific input. Use a runtime error when the failure stems from business logic or external state that cannot be detected by input validation alone.
</Accordion>
